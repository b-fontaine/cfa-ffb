# Recherche — Persistance locale multi-plateforme (6 cibles) pour le suivi d'élèves de Blackball - comparatif drift / sembast / isar_community / hive_ce / objectbox / shared_preferences / sqflite_common_ffi, et architecture recommandée

> Produit par un agent de recherche le 2026-10-11 (sources citées). **Les versions sont à revalider par `flutter pub get` avant usage.** Les faits de confiance `medium` ou `low` ne sont pas vérifiés dans le dépôt.

## Recommandation

Recommandation unique : drift (2.35.x) + drift_flutter (0.3.x), SQLite sur les 6 cibles (natif via build hooks sqlite3 3.x, wasm sur web), sans sqlite3_flutter_libs. Justification : seul candidat cumulant 6 cibles officielles, maintenance très active en octobre 2026, migrations outillées et testables (make-migrations), base in-memory triviale pour tests unitaires et BDD (NativeDatabase.memory()), requêtes relationnelles/agrégats adaptées au suivi d'élèves (élève -> séances -> résultats d'exercices, moyennes de taux de réussite par élève/compétence), et un gabarit de données qui se mappe naturellement vers Firestore. Alternative légère acceptable : sembast (Dart pur, sans codegen, très simple, in-memory via sembast_memory) si vous préférez éviter le setup wasm/worker du web, au prix de migrations manuelles et d'un modèle non relationnel. À écarter : objectbox et isar_community (pas de web), hive_ce (pas de requêtes/migrations), shared_preferences (réglages uniquement), sqflite_common_ffi (redondant, SQL brut).

Architecture (Clean + FSD), par feature (ex. features/suivi_eleves) :
1. domain/ : entités Dart pures (freezed) Eleve, SuiviSeance, ResultatExercice ; interfaces abstraites ElevesRepository, SuiviRepository (Future/Stream) ; use cases (enregistrerResultat, bilanEleve, exporterSauvegarde, importerSauvegarde). Aucune dépendance drift/Flutter. Ajouter un format de sauvegarde JSON versionné (champ schemaVersion, liste élèves + suivis) défini dans le domaine (DTO + SauvegardeCodec).
2. data/local/ : AppDatabase (drift) avec tables, DAOs, mappers table<->entité ; DriftElevesRepository implements ElevesRepository ; constructeur AppDatabase(QueryExecutor) pour injection ; ouverture via driftDatabase(name: 'billard_cfa', web: DriftWebOptions(sqlite3Wasm: Uri.parse('sqlite3.wasm'), driftWorker: Uri.parse('drift_worker.js'))) ; enregistrement dans injectable/get_it (@LazySingleton, @module).
3. data/memory/ (ou test/support/) : InMemoryElevesRepository (Map/StreamController) comme fake pur Dart pour tests unitaires/BLoC et steps bdd_widget_test les plus rapides ; une seconde option est DriftElevesRepository sur NativeDatabase.memory() pour tester les vraies requêtes et migrations. Écrire une suite de tests de contrat unique exécutée contre les deux implémentations.
4. Export/import : use cases qui sérialisent via le codec JSON ; fichier écrit/partagé avec share_plus ou enregistré via file_picker (web : téléchargement ; import : file_picker -> parse -> transaction drift unique avec validation de schemaVersion et stratégie fusion/remplacement).
5. Migrations : schemaVersion + dart run drift_dev make-migrations, tests générés conservés en CI ; le format de sauvegarde JSON garde son propre numéro de version indépendant du schéma SQL.
6. Évolution Firebase (si synchronisation multi-appareils) : ajouter FirestoreElevesRepository implements la même interface (Auth + Firestore, collections par animateur : users/{uid}/eleves/...), puis un SyncingRepository décorateur (local drift = source de lecture, file d'attente d'écritures, last-write-wins par updatedAt, ids UUID générés côté client, colonnes updatedAt/deletedAt/syncedAt à prévoir dès le schéma v1). Alternative simple : activer la persistance offline native de Firestore et garder drift uniquement comme cache. Aucun changement dans domain/ ni dans les BLoC.
7. Dès maintenant, prévoir dans le schéma : id UUID texte, createdAt/updatedAt, suppression logique, et ne pas stocker de données personnelles inutiles (élèves mineurs, RGPD) ; chiffrement éventuel via sqlcipher_flutter_libs seulement si exigé.

## Faits relevés

- **[high]** drift 2.35.2 publié le 2026-10-07 (drift_dev 2.35.1 le 2026-09-30), SDK >=3.10 <4. Tags pub.dev : android, ios, windows, linux, macos, web, wasm-ready, Flutter Favorite ; 160/160 pts, ~2479 likes, ~1,5 M téléchargements/30j. Très activement maintenu.
  - Source : https://pub.dev/api/packages/drift ; https://pub.dev/api/packages/drift/score
- **[high]** drift_flutter 0.3.1 (2026-07-11) : une seule fonction driftDatabase(name:, web: DriftWebOptions(...)) couvre natif et web ; plateformes Android, iOS, Linux, macOS, Windows, web. Fichier natif $name.sqlite dans getApplicationDocumentsDirectory() (path_provider) ; dépend de drift ^2.30, sqlite3 ^3.0.0.
  - Source : https://pub.dev/packages/drift_flutter ; https://pub.dev/api/packages/drift_flutter
- **[high]** Web drift : WasmDatabase (SQLite compilé en WebAssembly), nécessite sqlite3.wasm et drift_worker.dart.js dans web/ (même version de drift) et Content-Type application/wasm. Meilleur stockage (OPFS) avec en-têtes COOP same-origin + COEP require-corp/credentialless, sinon repli IndexedDB partagé, voire in-memory sans persistance (à détecter via chosenImplementation/missingFeatures). Les en-têtes peuvent casser certaines popups Google Auth (point d'attention pour Firebase Auth plus tard) ; WebDatabase ancien est déprécié.
  - Source : https://drift.simonbinder.eu/platforms/web/ ; https://drift.simonbinder.eu/platforms/
- **[high]** sqlite3_flutter_libs n'est plus nécessaire depuis drift 2.32.0 avec sqlite3 3.x (SQLite fourni par build hooks) ; sqlite3_flutter_libs 0.6.0+eol (2026-02-15) est marqué « Not used anymore ». sqlite3 3.7.0 publié 2026-09-30.
  - Source : https://drift.simonbinder.eu/platforms/ ; https://pub.dev/api/packages/sqlite3_flutter_libs ; https://pub.dev/api/packages/sqlite3
- **[high]** Tests drift : le constructeur de la base prend un QueryExecutor ; en test on passe DatabaseConnection(NativeDatabase.memory(), closeStreamsSynchronously: true) puis database.close() en tearDown. Aucune doc de test web/wasm dans cette page.
  - Source : https://drift.simonbinder.eu/testing/
- **[high]** Migrations drift : schemaVersion + MigrationStrategy (onCreate/onUpgrade/beforeOpen), et outil 'dart run drift_dev make-migrations' qui versionne les snapshots de schéma (drift_schemas/), génère *.steps.dart (stepByStep) et des tests de migration dans test/drift/. Approche la plus outillée du comparatif.
  - Source : https://drift.simonbinder.eu/migrations/
- **[medium]** Compatibilité codegen drift : drift_dev est un générateur build_runner standard ; coexiste avec freezed/injectable (builders distincts, fichiers .g.dart/.drift.dart). Tables SQL typées distinctes des entités du domaine : il faut des mappers, ce qui convient à Clean Architecture. Export/import JSON : pas de fonction clé en main vérifiée dans cette recherche ; à écrire (lecture des tables -> JSON versionné -> transaction d'import).
  - Source : https://drift.simonbinder.eu/migrations/ ; inférence d'architecture

## Risques

- Web drift : sqlite3.wasm et drift_worker.dart.js doivent être copiés dans web/ à la même version que drift et servis avec Content-Type application/wasm ; sans en-têtes COOP/COEP, repli sur IndexedDB (moins performant) ; ces en-têtes peuvent casser les popups Google Auth, donc à arbitrer lors du passage à Firebase Auth sur web.
- Sur web, si le navigateur ne fournit aucune implémentation persistante, drift retombe en in-memory : il faut vérifier chosenImplementation et avertir l'utilisateur / proposer l'export JSON.
- drift_flutter est en 0.x (0.3.1) : API potentiellement moins stable que drift 2.x ; épingler les versions et aligner drift et drift_dev (2.35.x).
- Fusion de drift_dev, freezed 4, injectable 3 et build_runner : conflits possibles de versions de analyzer/source_gen ; à valider par un flutter pub get + build_runner à blanc avant d'engager (non testé dans cette recherche, dépôt non modifié).
- Export/import JSON non fourni par drift : à implémenter et à tester (idempotence, version de format, import transactionnel, gestion des conflits).
- sembast : exportDatabase/importDatabase et fabrique mémoire non vérifiés sur la doc d'API (confidence medium) ; migrations manuelles sans outil de test.
- isar_community : dernière release en mars 2026, pas de web, téléchargement de binaire natif en test ; fork communautaire dont la pérennité dépend de peu de mainteneurs.
- shared_preferences et localStorage web : quotas navigateur et effacement possible des données du site ; toute persistance web locale doit être doublée par la sauvegarde JSON exportable.
- Données d'élèves mineurs : obligations RGPD (minimisation, consentement, durée de conservation) à anticiper surtout avant toute synchronisation cloud.
- Les versions sont celles de pub.dev au 2026-10-11 ; les numéros peuvent évoluer entre cette recherche et l'implémentation.
